# ГОЛОСОВАНИЕ

## 1. Описание сервиса для участников

Напишем сюжет мультфильма вместе. Зарегистрированные игроки предлагают продолжение, все желающие (в том числе гости) голосуют за идеи. Каждые пять минут раунд закрывается: победившая реплика дописывается в сюжет, начинается следующий круг.

Голосовать можно без аккаунта: один голос с одного адреса за раунд. Чтобы запостить свою идею, нужна регистрация — слот один на игрока на раунд, до конца голосования идею можно снять. У опубликованной идеи есть скрытый журнал просмотров: автор видит, кто открывал материал по его ссылке.

## 2. Подробное описание функционала

### 2.1. Состав стенда

| Сервис | Образ / стек | Роль |
|--------|----------------|------|
| `web` | Flask + APScheduler, SQLite | Форум, Story Lab, журналы просмотров идей, прокси к боту |
| `bot` | Express + Puppeteer + Chromium | Модератор: открывает URL и несёт флаг в cookie |

Флаг задаётся в `docker-compose.yml` как `FLAG` и попадает в cookie бота `flag` (не `HttpOnly`, домен `web`).

```
клиент  →  http://127.0.0.1:5001  (web:5000)
                └─ POST /report  →  http://bot:3000/visit
                       бот открывает URL с cookie flag
```

Сеть Docker: `untitled-dom-clob`. Приложение монтируется как `./app:/app`, база — `ctf.db` в каталоге приложения.

### 2.2. Приложение: маршруты

Flask слушает `:5000` внутри контейнера, наружу проброшен `:5001`.

| Метод | Путь | Назначение |
|-------|------|------------|
| `GET` | `/` | Главная: сюжет, идеи текущего раунда, история победителей |
| `GET`/`POST` | `/register` | Регистрация |
| `GET`/`POST` | `/login` | Вход, сессия по `user_id` |
| `POST` | `/logout` | Сброс сессии |
| `GET` | `/suggest/new` | Форма своей идеи (нужен логин) |
| `POST` | `/suggest` | Добавить идею в текущий раунд |
| `POST` | `/suggest/<id>/delete` | Удалить свою pending-идею |
| `GET` | `/vote` | Доска голосования |
| `POST` | `/vote/<id>` | Отдать голос (логин не обязателен) |
| `GET` | `/story-lab` | Контактная форма: query `firstname`, `lastname`, `email` |
| `GET`/`POST` | `/report` | Отправить URL боту |
| `GET`/`POST` | `/views/<key>` | Журнал просмотров идеи; `GET ?viewer=` записывает зрителя |

Секрет приложения: `SECRET_KEY` из окружения (`ctf-local-secret` в compose). Интервал раунда: `ROUND_INTERVAL_SECONDS` (по умолчанию `600`).

### 2.3. Пользователи и сессии

Пароли хранятся через `werkzeug.security.generate_password_hash`. При старте в таблицу `users` кладётся служебная запись `id=0`, `username=guest` — ею помечаются голоса без логина (`session.get("user_id", 0)`).

Декоратор `@login_required` стоит только на `/suggest`, `/suggest/new` и удалении идеи. Голосование и Story Lab открыты всем.

### 2.4. Сюжет и раунды

Состояние сюжета — одна строка `story_state` с `id=1`: `current_story`, `current_round`, `updated_at`. Стартовый текст:

```
В Городе Мультландии главный герой Флик нашел волшебный карандаш,
который оживляет любой нарисованный объект.
```

`BackgroundScheduler` раз в `ROUND_INTERVAL_SECONDS` вызывает `finish_round()`:

1. Берёт pending-идеи текущего раунда, сортирует по числу голосов (у равенства — более ранняя).
2. Победителю ставит `status=winner`, остальным — `rejected`.
3. Текст победителя дописывается к `current_story` через перевод строки.
4. Запись уходит в `story_history`, `current_round` увеличивается на 1.
5. Если идей не было — в историю пишется `(Раунд завершен без новых идей.)`.

На главной показываются pending-идеи текущего раунда и последние 10 записей истории. В шаблонах форума контент идей идёт через обычный Jinja (`{{ item.content }}`): автоэкранирование включено, HTML из идей не исполняется.

### 2.5. Идеи и голосование

Правила идей:

- непустой текст, максимум 500 символов;
- не больше одной pending-идеи на пользователя в раунде;
- удалить можно только свою pending-идею текущего раунда (вместе с её голосами).

Правила голоса:

- идея должна быть `pending` в текущем раунде;
- с одного IP — один голос на раунд (проверка запросом по `votes ⨝ suggestions`);
- плюс уникальность `(suggestion_id, voter_ip)` на уровне SQLite.

IP берётся из первого значения `X-Forwarded-For`, иначе из `request.remote_addr`. Заголовку доверяют без ограничений — это не целевой путь к флагу, но влияет на антифрод голосования.

### 2.6. Story Lab

`GET /story-lab?firstname=&lastname=&email=` рисует три `<input>` и превью `#selected_email`. Значения подставляются через `|safe`:

```html
<input name="user_first_name" value="{{ firstname|safe }}">
<input name="user_last_name"  value="{{ lastname|safe }}">
<input id="email" name="email" value="{{ email|safe }}">
```

Перед рендером вызывается `reject_direct_tags`: если в любом из трёх параметров есть совпадение с `<[a-zA-Z]`, страница отвечает `500` и текстом `An error occurred`. Закрывающие теги, атрибуты и HTML-сущности фильтр не режет.

На странице подключены:

- jQuery 3.7.1 с `ajax.googleapis.com`;
- `https://www.google.com/recaptcha/api.js`;
- `/static/subscribe.js`.

В `subscribe.js` один гаджет:

```javascript
function subscribereport() {
  const email = $("#email").val();
  $("#selected_email").html(email);
}
```

Функция нигде в разметке не вызывается напрямую: её должен дёрнуть кто-то ещё. `subscribereport` читает `.val()` у `#email` и скармливает строку в `.html()` — это HTML-sink. Сама страница не содержит виджета reCAPTCHA; скрипт Google всё равно загружается и ищет элементы `.g-recaptcha`.

### 2.7. CSP

Заголовок вешается на все ответы Flask:

```
default-src 'self' https://www.google.com https://www.gstatic.com
  https://ajax.googleapis.com https://cdnjs.cloudflare.com
  https://fonts.googleapis.com https://fonts.gstatic.com data:;
style-src 'self' 'unsafe-inline' https://fonts.googleapis.com;
font-src 'self' https://fonts.gstatic.com data:;
img-src 'self' data: https:;
```

`script-src` нет — для скриптов действует `default-src`. Итог:

- инлайн-скрипты и обработчики вроде `onerror=` запрещены (`'unsafe-inline'` только в `style-src`);
- внешние скрипты — `'self'`, Google (reCAPTCHA), `ajax.googleapis.com`, `cdnjs`, шрифты;
- схемы `data:` в `default-src` разрешены, значит `<script src="data:text/javascript,...">` проходит;
- `frame-src` тоже наследуется из `default-src`.

### 2.8. Бот-модератор

`POST /report` (query `url` на GET тоже принимается):

- относительный путь `/...` превращается в `http://web:5000/...`;
- дальше `POST http://bot:3000/visit` с JSON `{"url": ...}`.

Бот (`bot.js`):

1. Пускает только `http://web:5000/`, `http://localhost:5000/`, `http://127.0.0.1:5000/`.
2. Ставит cookie `flag=<FLAG>` на домен `web`, путь `/`, `httpOnly: false`, `secure: false`.
3. Кладёт URL в очередь и сразу отвечает `Queued`, визиты идут по одному (общий Chromium).
4. Открывает URL (`networkidle2`, таймаут 5 с), ждёт ещё 3 с, закрывает вкладку.

Флаг живёт только в этом cookie. На форуме и в SQLite его нет.

### 2.9. Журнал просмотров идеи

Стенд общий. У каждой идеи свой `view_key` (`uuid4().hex`, 32 символа). Ссылка `/views/<key>` есть только на странице «Моя идея», на общую доску не выводится.

| Способ | Поведение |
|--------|-----------|
| `GET /views/<key>` | журнал этой идеи; неизвестный ключ → `404` |
| `GET /views/<key>?viewer=...` | дописывает зрителя и показывает журнал |
| `POST /views/<key>` поле `viewer` | то же через форму «Отметиться» |

Список зрителей не общий: без ключа чужой журнал не прочитать, id идеи на доске для этого не годится. Текст до 2000 символов, в шаблоне экранируется. XSS бота пишет cookie в `?viewer=` журнала **своей** идеи.

### 2.10. Запуск

```bash
cd voting
docker compose up --build
```

Сервис: `http://127.0.0.1:5001`.

Эталонный эксплойт (из корня задания):

```bash

```

Нужен пакет `requests`. Солвер регистрируется, постит идею, шлёт payload боту через `/report` и опрашивает `/views/<key>` своей идеи.

## 3. Подробный разбор решения

Флаг нигде не лежит на диске и не прячется в сюжете. Он живёт только в cookie бота-модератора. Значит, задача сводится к одному: выполнить свой JavaScript в браузере бота, прочитать `document.cookie` и переслать его туда, куда мы потом сможем заглянуть. Весь разбор — это дорога к такому XSS и аккуратная доставка флага обратно к нам.

### 3.1. Что видно при осмотре

Форум с голосованием — это декорация. Идеи на главной экранируются Jinja, голоса и раунды к флагу не ведут. Интереснее то, что стоит в стороне от основного сценария:

- **`/story-lab`** — «контактная форма». Три параметра из query (`firstname`, `lastname`, `email`) подставляются прямо в атрибуты `value` через фильтр `|safe`, то есть без экранирования:

```startLine:38:40:voting/app/templates/story_lab.html
                        <span>Почта</span>
                        <input id="email" name="email" value="{{ email|safe }}">
```

- **`/report`** принимает относительную ссылку и скармливает её боту. Бот ходит на `web` с cookie `flag`, причём cookie не `HttpOnly` — значит, из JS её видно.
- **`/views/<key>`** — приватный журнал просмотров идеи. Ключ знает только автор идеи, и всё, что пришло в `?viewer=...`, туда записывается и потом показывается. Идеальное место, чтобы «поймать» украденную cookie.

Общая картина складывается сама: отравить `/story-lab`, заставить бота выполнить там наш скрипт, а скрипт пусть отправит cookie в журнал нашей идеи. Остаётся понять, почему «в лоб» это не работает, и обойти три препятствия.

### 3.2. Три препятствия на пути к XSS

Наивная попытка — просто передать `<script>` или `<img onerror=...>` в параметры — разбивается о защиту:

1. **Фильтр тегов.** Перед рендером `/story-lab` проверяет параметры регуляркой `<[a-zA-Z]`. Любой прямой тег → ответ `500`. Так что ни `<script`, ни `<iframe` в query написать нельзя.
2. **CSP.** Заголовок запрещает инлайн-скрипты: `'unsafe-inline'` есть только для стилей, но не для `script`. Поэтому `onerror=...` и инлайн-обработчики не сработают, даже если протащить их мимо фильтра.
3. **Контекст вставки.** Наши значения попадают всего лишь в атрибут `value` у `<input>`. Сами по себе они ничего не исполняют — нужен кто-то, кто возьмёт это значение и превратит его в живой HTML.

То есть нужно: сломать атрибут **без угловых скобок**, найти функцию, которая сама вставит наш HTML на страницу, и подобрать такой скрипт, который переживёт и фильтр, и CSP.

### 3.3. Кто вставит наш HTML: гаджет и sink

На странице подключён `subscribe.js` с единственной функцией:

```startLine:1:4:voting/app/static/subscribe.js
function subscribereport() {
  const email = $("#email").val();
  $("#selected_email").html(email);
}
```

Это и есть наш sink: функция берёт значение инпута `#email` и вставляет его через jQuery `.html()` — то есть как настоящий HTML, а не как текст. Два вопроса: как подсунуть сюда свой HTML и кто вызовет `subscribereport()` (в разметке её никто не дёргает).

Оба вопроса решает приём с **DOM clobbering** и гаджетом reCAPTCHA. Ломаем кавычку в `value` и дописываем атрибуты к инпутам.

Через `lastname` превращаем соседний инпут в поддельный виджет reCAPTCHA:

```
x" class="g-recaptcha" data-sitekey="1337" data-error-callback="subscribereport">
```

Подключённый `recaptcha/api.js` находит элемент с классом `g-recaptcha`, пытается отрисовать виджет по ключу `1337`, спотыкается и зовёт колбэк ошибки из `data-error-callback`. А там указано имя нашей функции — `subscribereport`. Так гаджет сам вызывает sink, без валидного site key и без единого инлайн-скрипта.

Через `firstname` вешаем `id=email` на **свой** инпут. jQuery в `$("#email")` берёт первый элемент с таким id в дереве — и это уже не штатное поле почты, а наш инпут, в `value` которого лежит полезная нагрузка. Угловых скобок в параметрах нет, поэтому фильтр молчит: в `lastname` только кавычки и атрибуты, в `firstname` нагрузка спрятана в HTML-сущностях.

### 3.4. Как обойти CSP: `srcdoc` + `data:`

Осталось главное препятствие — CSP, которая не даёт выполнить инлайн-код. Хитрость в том, что `.html()` у jQuery вырезает голый `<script>`, но спокойно вставляет `<iframe>`. А документ внутри `srcdoc` iframe — это уже отдельная страница, и там можно подключить скрипт через `src="data:..."`, который CSP как раз разрешает.

Полезная нагрузка (та, что лежит в `value` нашего инпута) записана сущностями, чтобы пройти фильтр, а в DOM браузер раскодирует её обратно в живой HTML:

```
&lt;iframe srcdoc=&quot;
  &lt;script src=&quot;data:text/javascript,fetch('/views/VIEW_KEY?viewer='+encodeURIComponent(document.cookie))&quot;&gt;&lt;/script&gt;
&quot;&gt;&lt;/iframe&gt;
```

Пошагово всё сходится так:

1. Фильтр не видит тегов — в query только сущности.
2. Браузер раскодирует сущности в атрибуте `value`; `$("#email").val()` вернёт уже настоящий HTML.
3. `subscribereport()` кладёт этот HTML через `.html()` — на странице появляется `<iframe srcdoc="...">`.
4. Внутри `srcdoc` грузится `<script src="data:text/javascript,...">`. Схема `data:` разрешена CSP, `'unsafe-inline'` не нужен.
5. Скрипт исполняется в контексте `web`, читает `document.cookie` (а там флаг) и отправляет его в `/views/VIEW_KEY` нашей идеи.

После этого достаточно открыть журнал своей идеи и прочитать флаг.

Коротко по шагам во времени:

```
бот открывает /story-lab?firstname=...&lastname=...
  → браузер строит инпуты с id=email и class=g-recaptcha
  → recaptcha/api.js спотыкается и зовёт subscribereport()
  → .html() вставляет iframe + srcdoc + data:-скрипт
  → fetch /views/VIEW_KEY?viewer=<document.cookie с флагом>
автор идеи открывает /views/VIEW_KEY и видит флаг
```

### 3.5. Эталонный эксплойт

`solver.py` проходит всю цепочку автоматически:

1. Регистрируется, постит идею и забирает её `view_key` со страницы «Моя идея» — это адрес нашего журнала.
2. Собирает query для `/story-lab`: в `firstname` — нагрузка с iframe/`srcdoc`/`data:`-скриптом и `" id=email>`, в `lastname` — поддельный `.g-recaptcha` с `data-error-callback=subscribereport`. Скрипт внутри делает `fetch('/views/<key>?viewer='+document.cookie)`.
3. Отправляет эту ссылку боту через `POST /report`.
4. Опрашивает `GET /views/<key>`, пока в журнале не появится `CyberCTF{...}`.

```bash
python3 solver.py --base http://127.0.0.1:5001
```

Ожидаемый вывод: `[+] FLAG: CyberCTF{...}` (значение берётся из `FLAG` у бота).

Вручную путь тот же: запостить идею, подставить её `view_key` в нагрузку, отправить ссылку в `/report`, подождать и открыть «Кто смотрел». Payload удобно собирать через `urllib.parse.quote` — внутри `srcdoc` легко запутаться в кавычках и сущностях.

Небольшая деталь про общий стенд: бот обрабатывает визиты по очереди, поэтому `/report` сразу отвечает `Queued`, а запись в журнале появляется, когда очередь дойдёт до нашей ссылки.
