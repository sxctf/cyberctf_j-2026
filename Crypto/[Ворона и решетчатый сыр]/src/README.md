# Ворона и решетчатый сыр

**Категория:** crypto / lattices  
**Сложность:** hard

---

## Описание задания для участников

	Вороне где-то бог послал кусочек сыру;
    На ель Ворона взгромоздясь,
    Позавтракать было совсем уж собралась...

Сыр решётчатый: дырки в нём стоят по узлам решётки L в Z^M. Ворона
клюнула рядом с одной из дырок (скрытая точка решётки), промахнувшись
на малый вектор e. Лисица видит след клюва (вектор t) и знает рецепт
сыра — но лишь в скособоченных координатах (публичный базис). Ключ от
флага — точное положение следа относительно дырки, вектор e.

### Что выдаётся

- `challenge.py` — как именно варился сыр, куда клюнула Ворона и как
  шифровался флаг. Секретов в файле нет: вся случайность бралась из
  системного генератора и не сохранялась.
- `challenge.json` — публичные данные: размерность, модуль, рецепт сыра
  (базис решётки, строки — векторы), след клюва (`target`) и
  зашифрованный флаг.

Сервера нет. Всё, что нужно, уже в двух файлах.

## Подробное описание функционала

Статический генератор. `challenge.py` один раз строит случайную
q-арную решётку, прячет в ней точку, сдвигает её на малый вектор и
шифрует флаг ключом, выведенным из этого сдвига. Оракула и сетевого
сервиса нет.

### Состав

| Компонент | Путь | Роль |
|-----------|------|------|
| Генератор | `crow-lattice-cheese/challenge.py` | решётка, цель, шифрование флага |
| Публичные данные | `crow-lattice-cheese/challenge.json` | то, что видит участник |
| Решение | `solve.py` | только для организатора, нужен fpylll |

Участникам отдаются `challenge.py` и `challenge.json`. `solve.py` на
площадку не попадает. Флаг читается из `FLAG`; `challenge.json` в
репозитории собран с заглушкой `flag{THIS_IS_FAKE_FLAG}` и перед
выдачей пересобирается с боевым флагом.

```bash
FLAG='flag{...}' python3 crow-lattice-cheese/challenge.py crow-lattice-cheese/challenge.json
```

### Параметры

```text
M            = 160    размерность решётки
N            = 80     ранг свободной части
Q            = 4093   модуль
CHEESE_BOUND = 5      |e_i| <= 5
DOMAIN       = "crow-lattice-cheese-v2"
```

### Решётка

Случайная матрица `A'` размера `N × (M − N)` с элементами из `ℤ_Q`.
Решётка

```text
L = { x · [ I_N | A' ]  mod Q  :  x ∈ ℤ^N }  +  Q·ℤ^M
```

Иначе: вектор `v ∈ ℤ^M` лежит в `L`, когда его хвост из `M − N`
координат сравним по модулю `Q` с `v_head · A'`. Публичный базис —
строки матрицы `M × M`:

```text
[ I_N   A'  ]      первые N строк
[  0   Q·I  ]      остальные M − N строк
```

Определитель `det L = Q^(M−N) = 4093^80`. Это «скособоченный»
базис: он содержит векторы длины `Q = 4093`, тогда как кратчайший
ненулевой вектор решётки по гауссовой эвристике

```text
λ₁ ≈ √(M / 2πe) · Q^((M−N)/M) ≈ 3.06 · 64 ≈ 196
```

Ячейка Вороного нуля содержит шар радиуса `λ₁/2 ≈ 98`.

### Цель

```text
hole    ∈ ℤ_Q^N                   случайная дырка
point   = hole · [I | A'] mod Q    точка решётки
e       ∈ [−5, 5]^M                сдвиг следа клюва от дырки
target  = point + e  mod Q         след клюва
```

Дисперсия одной координаты `5·6/3 = 10`, поэтому `‖e‖ ≈ √(160·10) = 40`;
на практике `38–40`. Это заметно меньше `λ₁/2 ≈ 98`, то есть `e`
лежит внутри ячейки Вороного
своей дырки, и `target` однозначно декодируется в `point`. Генератор
проверяет `‖e‖ < GH/2` и падает, если сыр «вылез».

### Шифрование флага

```text
key      = SHA-256( DOMAIN ‖ "|" ‖ "e₀ e₁ … e₁₅₉" )
stream_i = SHA-256( key ‖ i₃₂ )
ct       = flag ⊕ stream
```

Координаты `e` сериализуются как десятичные целые со знаком через
пробел. Ключ зависит только от `e`; зная `hole`, `e` вычисляется
как `target − point mod Q` с центрированием в `[−Q/2, Q/2)`.

### Формат `challenge.json`

| Поле | Тип | Смысл |
|------|-----|-------|
| `m`, `n`, `q` | int | параметры решётки |
| `cheese_bound` | int | граница на `|e_i|` |
| `basis` | `m × m` int | строки — базисные векторы `L` |
| `target` | `m` int | `point + e mod q` |
| `ciphertext` | hex | флаг под ключом из `e` |

Размер файла около 100 КБ.

## Разбор

### TLDR

Это BDD в q-арной решётке размерности 160: `target` лежит на
расстоянии `‖e‖ ≈ 39` от точки решётки, а ближайшие чужие точки — на
`≈ 196`. Вложение Каннана делает из `e` кратчайший вектор решётки
размерности 161. Используем алгоритм BKZ для получения ключа `e` и флага.

### Подробный разбор решения

Даны базис `L`, вектор `target`, граница `|e_i| ≤ 5`. Секрет:
либо `hole` (80 координат из `ℤ_Q`), либо `e` (160 малых координат).
Одно восстанавливается из другого, ключ строится из `e`.

Генератор берёт случайность из
`secrets.SystemRandom` и ничего не сохраняет; `challenge.py` сообщает
только распределение: решётка случайная, сдвиг равномерный на
`[−5, 5]`.

Ячейка Вороного точки `p ∈ L` — все векторы, которым `p` ближе любой
другой точки решётки. Для случайной решётки она содержит шар радиуса
`λ₁/2 ≈ 98`. Сдвиг `e` имеет длину около `39`, то есть `target`
лежит глубоко внутри ячейки своей дырки. Поэтому задача корректна:
ближайшая точка одна, и это `point`. Поэтому же у неё нет обходного
пути: чтобы найти центр ячейки, нужно уметь декодировать в этой
решётке, а публичный базис этого не умеет.

В базисе лежат векторы `Q·e_j` длины `4093` и строки `(e_i, A'_i)`
с элементами до `Q`. Округление Бабаи в таком базисе ошибается на
величины порядка `Q/2`, а не `5`. Нужен редуцированный базис.

Собираем матрицу `(M+1) × (M+1)`:

```text
[ b₀      0 ]
[ …       … ]
[ b₁₅₉    0 ]
[ target  S ]       S = cheese_bound = 5
```

Её строки порождают решётку `L'`. В ней есть вектор

```text
(target, S) − (point + Q·k, 0) = (e, S),    ‖(e, S)‖ ≈ 39.3
```

Остальные векторы `L'` не короче `λ₁(L) ≈ 196`. Разрыв

```text
λ₂(L') / λ₁(L') ≈ 196 / 39 ≈ 5
```

Это unique-SVP с разрывом 5 в размерности 161.

Идея решения подобных задач следующая:
(1) переписать задачу так, чтобы искомое стало
необычно коротким вектором некоторой решётки;
(2) прогнать базис
через алгоритм редукции;
(3) прочитать ответ из первых строк
редуцированного базиса. 
Шаг (1) здесь — вложение Каннана. Шаг (3) —
поиск строки с `±S` в последней координате. Вся сложность в шаге (2).

Редукция базиса — замена данного базиса на другой базис **той же**
решётки, у которого векторы короче и ближе к ортогональным. Любые два
базиса связаны унимодулярной матрицей, поэтому «скособоченный» базис
из `challenge.json` и короткий базис, который видит Ворона, порождают
одну и ту же решётку; редукция восстанавливает второй из первого.

Ключевой объект — ортогонализация Грама–Шмидта `b₁*, …, b_d*`: вектор
`b_i*` — это `b_i` минус его проекция на `span(b₁, …, b_{i−1})`.
Длины `‖b_i*‖` образуют *профиль* базиса. Произведение `∏ ‖b_i*‖`
равно `det L` и не меняется при редукции, поэтому редукция может
только перераспределять длины: делать первые `‖b_i*‖` короче за счёт
того, что последние станут длиннее. Чем ровнее профиль, тем лучше
базис. У плохого базиса профиль — обрыв: первые `80` строк `(e_i, A'_i)`
дают `‖b_i*‖ ≈ Q`, остальные — `≈ 1`.

Основные алгоритмы реализации этой идеи: LLL и BKZ.

Алгоритм Ленстры–Ленстры–Ловаса (LLL). Базис называется
LLL-редуцированным с параметром `δ ∈ (1/4, 1)`, если

```text
|μ_{i,j}| ≤ 1/2                              size reduction
δ · ‖b_{i−1}*‖² ≤ ‖b_i*‖² + μ²_{i,i−1} ‖b_{i−1}*‖²   условие Ловаса
```

где `μ_{i,j} = ⟨b_i, b_j*⟩ / ‖b_j*‖²` — коэффициенты Грама–Шмидта.
Первое условие говорит, что каждый `b_i` уже «почти ортогонален»
предыдущим — из него вычтены ближайшие целые кратные. Второе
запрещает профилю падать слишком резко: соседние `‖b_i*‖` отличаются
не более чем в `≈ 1/√(δ − 1/4)` раз, при `δ = 0.99` это `≈ 1.16`.

Алгоритм прост: идём по базису, size-reduce'им `b_i`, проверяем
условие Ловаса; если оно нарушено — меняем `b_i` и `b_{i−1}` местами и
откатываемся на шаг назад. Каждый своп уменьшает потенциал
`∏ ‖b_i*‖^{2(d−i)}` хотя бы в `1/δ` раз, отсюда полиномиальное
время: `O(d⁵ · log B)` операций над числами длины `log B` в наивном
варианте, на практике — секунды для `d ≈ 160`.

Гарантия: `‖b₁‖ ≤ (4/3)^{(d−1)/4} · det^{1/d}`, то есть первый вектор
не длиннее `det^{1/d}` более чем в `1.075^d` раз. На случайных
решётках LLL ведёт себя лучше теории: *корневой фактор Эрмита*
`δ_LLL = (‖b₁‖ / det^{1/d})^{1/d} ≈ 1.022`. Для `d = 161` это
`‖b₁‖ ≈ 1.022^161 · 62 ≈ 2000` — ровно столько мы и видим после LLL.
Вектор длины `39` LLL в одиночку не найдёт: его условие Ловаса
локальное, оно смотрит только на соседние пары.

Block Korkine–Zolotarev (BKZ). Обобщение LLL, в
котором локальное условие на пару соседей заменено на условие на блок
из `β` векторов: для каждого `i` вектор `b_i*` должен быть кратчайшим
в проекции решётки `span(b_i, …, b_{i+β−1})` на ортогональное
дополнение к `span(b₁, …, b_{i−1})`. Проверка этого условия —
точное решение SVP в размерности `β`: перебор (enumeration Каннана /
Шнорра–Ойхнера с отсечением Гамы–Нгуена–Регева) или решето
(sieving). Алгоритм делает *туры*: проходит по всем блокам
`i = 1, …, d − 1`, в каждом вызывает SVP-оракул на блоке и вставляет
найденный короткий вектор, затем подчищает LLL. Тур повторяется,
пока базис меняется, или до лимита туров.

Два крайних случая: `β = 2` — это LLL, `β = d` — HKZ-редукция,
первый вектор равен `λ₁`. Между ними — непрерывная шкала
«качество ↔ время». Качество: корневой фактор Эрмита

```text
δ_β ≈ ( β / (2πe) · (πβ)^{1/β} )^{1 / (2(β−1))}
```

`δ₂₀ ≈ 1.0128`, `δ₃₀ ≈ 1.0109`, `δ₄₀ ≈ 1.0097`, `δ₆₀ ≈ 1.0083`.
Цена: SVP в размерности `β` стоит `2^{O(β log β)}` для перебора и
`2^{0.292β}` для решета, так что время растёт экспоненциально по `β`
и лишь полиномиально по `d`. На практике fpylll в один поток:
BKZ-20 — секунды, BKZ-40 — минуты, BKZ-60 — часы; дальше нужны
G6K и решето на GPU.

Прогрессивный BKZ — запускать блоки по возрастанию `10 → 20 → 30 → …`
на одном и том же базисе. Каждый следующий блок стартует с уже
хорошего базиса и сходится быстрее, чем если бы сразу запустили
большой `β`; это и делает `solve.py`.

Для случайной решётки BKZ-β даёт `‖b₁‖ ≈ δ_β^d · det^{1/d}`: при
`β = 30` это `≈ 5.7 · 62 ≈ 350`, всё ещё в девять раз длиннее `39`.
Но нам нужен не кратчайший вектор произвольной решётки, а *заведомо
существующий* аномально короткий. Он «выпадает» не из первого блока,
а из последнего: редукция выравнивает профиль, последние `‖b_i*‖`
растут, и в какой-то момент проекция `(e, S)` на последний блок
становится короче `‖b_{d−β}*‖` — SVP-оракул на этом блоке её
находит, после чего LLL-подчистка протаскивает вектор в начало
базиса за один тур. Оценка момента (Alkim–Ducas–Pöppelmann–Schwabe,
2016):

```text
σ · √β  ≲  δ_β^{2β − d} · det(L')^{1/d}
```

где `σ ≈ 3.2` — среднеквадратичное одной координаты `e`. При
`d = 161`, `det^{1/d} ≈ 62`: для `β = 30` правая часть `≈ 20.5`,
левая `≈ 17.5` — на грани; для `β = 40` правая `≈ 28`, левая
`≈ 20` — с запасом. Это объясняет, почему BKZ-30 срабатывает через
раз, а BKZ-40 — всегда, и почему `‖b₁‖` падает скачком с `≈ 700`
до `39`, а не плавно.

Инструменты: fplll / fpylll (C++ и Python, есть в Sage), G6K для
решета, flatter для быстрого LLL на больших входах. На CTF
стандартный путь — Sage или `pip install fpylll`, вложение Каннана,
прогрессивный BKZ.

На ноутбуке (fpylll 0.5.9 из Sage, один поток, 8 туров на блок),
четыре случайных экземпляра:

- LLL: `‖b₁‖ ≈ 1850`, 2–3 с. Вектор не найден.
- BKZ-10: `‖b₁‖ ≈ 1000`, +4 с. Вектор не найден.
- BKZ-20: `‖b₁‖ ≈ 720`, +6 с. Вектор не найден.
- BKZ-30: +11–15 с. На двух экземплярах из четырёх первая строка —
  `±(e, 5)`, на двух `‖b₁‖ ≈ 620` и вектора нет.
- BKZ-35: `‖b₁‖ ≈ 530`, +19 с. Не помогло там, где не хватило 30.
- BKZ-40: +170–180 с. Вектор найден.

Цифры совпадают с оценками выше: LLL даёт `≈ 2000`, граница
срабатывания unique-SVP лежит между блоками 30 и 40, поэтому
результат BKZ-30 зависит от экземпляра, а BKZ-40 проходит всегда.

При `|e_i| ≤ 3` хватает BKZ-20, при `|e_i| ≤ 4` BKZ-30 работал
стабильно, при `|e_i| ≤ 6` BKZ-40 в восемь туров за 157 с вектор не
нашёл. Пять — рабочая точка: LLL и BKZ-20 заведомо не хватает,
BKZ-30/40 проходят за минуты.


В найденной строке последняя координата равна `±5`. Знак выравнивается
по ней: если `−5`, вся строка умножается на `−1`. Первые 160 координат
— `e`. Проверка: все `|e_i| ≤ 5`, расшифрованный текст похож на флаг
(`\w+\{…\}`). Ключ и поток считаются так же, как в `challenge.py`.

Пример скрипта решения: `solve.py`.

```bash
sage -python solve.py crow-lattice-cheese/challenge.json
# или, если fpylll стоит в системном Python:
python3 solve.py crow-lattice-cheese/challenge.json
```

`solve.py` делает LLL, затем прогрессивный BKZ по блокам
`10 → 20 → 30 → 40 → 50`, после каждого шага ищет строку с `±5` в
конце и пробует расшифровать.
